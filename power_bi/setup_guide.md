# Power BI Setup Guide — NHS Finance Analytics

There is no `.pbix` file checked into this repository — like `data/raw/`, it's a large binary that
doesn't belong in version control. What *is* checked in, and is the source of truth for everything below,
is: the CSVs this guide imports (regenerated by `python/reporting/export_for_powerbi.py`), the real
measure set (`power_bi/dax_measures.md` and [`power_bi/dax/_Measures.tmdl`](dax/_Measures.tmdl)), and this
guide.

## 1. Connect to CSV Files

After running `python python/reporting/export_for_powerbi.py`, import these CSVs from
`data/processed/powerbi_export/`. Rename each table on import to match the `fact_`/`dim_` prefix used
throughout this guide and in the DAX measures — this is what Power BI's own model view shows once the
import is done (see the model diagram in `PROJECT_DOCUMENTATION.md`, stage ⑤):

| CSV file | Imported as | Rows | Description |
|------|------|------|-------------|
| `dim_trust.csv` | `dim_trust` | 215 | Provider master — org_code, sector, region, trust_type |
| `dim_financial_year.csv` | `dim_financial_year` | 5 | Calendar — 2019/20 to 2023/24 |
| `kpis.csv` | `fact_kpis` | 624 | Pre-built KPIs (1 row per trust per year) |
| `ie_summary.csv` | `fact_ie_summary` | 624 | I&E summary (income, expenditure, surplus) |
| `expenditure_breakdown.csv` | `fact_expenditure_breakdown` | 624 | Pay / non-pay / drugs split |
| `workforce.csv` | `fact_workforce` | 624 | Staff costs and WTE |
| `income_detail.csv` | `fact_income_detail` | 9,144 | Income by line item |
| `expenditure_detail.csv` | `fact_expenditure_detail` | 11,856 | Expenditure by line item |
| `profit_and_loss.csv` | `fact_profit_and_loss` | ~624 | Full statutory P&L (all real TAC02 SoCI/SOC lines) |
| `balance_sheet.csv` | `fact_balance_sheet` | ~624 | Full statutory Balance Sheet (all 40 TAC03 SoFP `BAL*` lines) |
| `sector_benchmarks.csv` | `fact_sector_benchmarks` | 30 | Aggregated sector totals |

### Import steps
1. **Get Data → Text/CSV** → select each file → Load
2. Rename each table in the **Fields** pane to the `fact_`/`dim_` name in the table above
3. On the **Home** tab, use **Transform Data** to verify column types:
   - `financial_year` → Text
   - `_000s` columns → Whole Number
   - `_pct` columns → Decimal Number
   - `org_code` → Text

## 2. Data Model Relationships

In Model view, create these relationships (all single-directional, many-to-one, into the two dimensions):

```text
fact_kpis[org_code]                     → dim_trust[org_code]
fact_kpis[financial_year]               → dim_financial_year[financial_year]
fact_ie_summary[org_code]               → dim_trust[org_code]
fact_ie_summary[financial_year]         → dim_financial_year[financial_year]
fact_expenditure_breakdown[org_code]    → dim_trust[org_code]
fact_expenditure_breakdown[financial_year] → dim_financial_year[financial_year]
fact_workforce[org_code]                → dim_trust[org_code]
fact_workforce[financial_year]          → dim_financial_year[financial_year]
fact_income_detail[org_code]            → dim_trust[org_code]
fact_income_detail[financial_year]      → dim_financial_year[financial_year]
fact_expenditure_detail[org_code]       → dim_trust[org_code]
fact_expenditure_detail[financial_year] → dim_financial_year[financial_year]
fact_profit_and_loss[org_code]          → dim_trust[org_code]
fact_profit_and_loss[financial_year]    → dim_financial_year[financial_year]
fact_balance_sheet[org_code]            → dim_trust[org_code]
fact_balance_sheet[financial_year]      → dim_financial_year[financial_year]
fact_sector_benchmarks[financial_year]  → dim_financial_year[financial_year]
```

`fact_sector_benchmarks` is the one fact table with no relationship to `dim_trust` — it has no `org_code`
column at all, since it's pre-aggregated by `sector`/`trust_type` in the SQL view rather than by
individual trust (see `sql/schema/create_tables_mysql.sql`, `v_kpis` grouped by sector). Its `sector` and
`trust_type` columns stay unmodelled attributes on the table itself rather than relationships.

`_Measures` (see section 3 below) sits outside this diagram entirely — it's a blank calculated table with no columns
that connect to anything, created purely to hold measures.

## 3. DAX Measures

Create a dedicated **`_Measures`** table (Enter Data → blank table named `_Measures`) and add every
measure to it — never to a fact table. The full set is 51 measures across seven families (base £m
conversions, KPI ratios, workforce, year-on-year comparisons, RAG status and colour, slicer-aware dynamic
text, sector benchmarking).

This guide doesn't duplicate them — that's how the table names drifted out of sync the first time. The
measures live in exactly one of two places, both kept in sync with each other:

- **[`power_bi/dax_measures.md`](dax_measures.md)** — every measure, grouped by family, in readable DAX,
  with a short note wherever a measure was planned but not built (or vice versa).
- **[`power_bi/dax/_Measures.tmdl`](dax/_Measures.tmdl)** — the exact `createOrReplace` definition
  exported from Power BI Desktop's TMDL view, including format strings and lineage tags. This is the file
  to trust if the two ever disagree.

## 5. NHS Colour Palette

The four RAG colours below are verified against the actual `*RAG Colour` measures in `_Measures` (see
`power_bi/dax_measures.md`, section 5, RAG Status Measures) — use these exact values for any conditional
formatting or RAG visual, not a close approximation:

```text
RAG Green (sustainable): #009639
RAG Amber (at risk):     #FFB81C
RAG Red (unsustainable): #DA291C
RAG Grey (no data):      #E8EDEE
```

General NHS brand colours for chart series, backgrounds, and text (not tied to a specific measure):

```text
NHS Blue:          #003087
NHS Dark Blue:     #002060
NHS Bright Blue:   #0072CE
NHS Orange:        #ED8B00
```
