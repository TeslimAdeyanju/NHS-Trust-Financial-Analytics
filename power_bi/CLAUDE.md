# Power BI Layer — DAX Conventions and Semantic Model Rules

## File

- No `.pbix` is checked into this repo — like `data/raw/`, it's a large binary kept out of version
  control. The rebuildable source of truth is: the CSVs in `data/processed/powerbi_export/`
  (regenerated by `python/reporting/export_for_powerbi.py`), the relationships and page specs in
  `power_bi/setup_guide.md`, and the measures in `power_bi/dax_measures.md` /
  [`power_bi/dax/_Measures.tmdl`](dax/_Measures.tmdl).
- Data source: the nine CSVs exported from MySQL (`nhs_finance`), imported via Get Data → Text/CSV.
  Power BI can alternatively DirectQuery `nhs_finance.v_*` directly — the views were designed to support
  it — but the CSV import is what's actually documented and used here.

### Relationships

```text
fact_kpis[org_code]                        → dim_trust[org_code]                 (Many-to-One)
fact_kpis[financial_year]                  → dim_financial_year[financial_year]  (Many-to-One)
fact_ie_summary[org_code]                  → dim_trust[org_code]                 (Many-to-One)
fact_ie_summary[financial_year]            → dim_financial_year[financial_year]  (Many-to-One)
fact_expenditure_breakdown[org_code]       → dim_trust[org_code]                 (Many-to-One)
fact_expenditure_breakdown[financial_year] → dim_financial_year[financial_year]  (Many-to-One)
fact_workforce[org_code]                   → dim_trust[org_code]                 (Many-to-One)
fact_workforce[financial_year]             → dim_financial_year[financial_year]  (Many-to-One)
fact_income_detail[org_code]               → dim_trust[org_code]                 (Many-to-One)
fact_income_detail[financial_year]         → dim_financial_year[financial_year]  (Many-to-One)
fact_expenditure_detail[org_code]          → dim_trust[org_code]                 (Many-to-One)
fact_expenditure_detail[financial_year]    → dim_financial_year[financial_year]  (Many-to-One)
fact_sector_benchmarks[financial_year]     → dim_financial_year[financial_year]  (Many-to-One)
```

`fact_sector_benchmarks` has no `org_code` and therefore no relationship to `dim_trust` — it's
pre-aggregated by `sector`/`trust_type` in SQL, not by individual trust. Cross-filter direction: **Single**
on every relationship.

## DAX Conventions

### Measure naming

- Use natural English names with Title Case: `Total Income (£m)`
- KPI measures use a `%` suffix: `EBITDA Margin %`
- YoY measures use a `YoY` marker: `Income YoY Growth %`, `EBITDA Margin YoY pp` (`pp` = percentage points,
  for a difference-of-percentages result, as distinct from a `%` growth rate)
- RAG status measures return the string `"Green"` / `"Amber"` / `"Red"` / `"Grey"`; the matching `... RAG
  Colour` measure maps that string to a hex code for conditional formatting

### Where measures live

Every measure — all 51 of them — is defined in a single dedicated `_Measures` table, not split across
multiple `.dax` files and not written inside a fact table. The two places that hold the actual
definitions:

- `power_bi/dax_measures.md` — human-readable, grouped into seven families (Core I&E, KPIs, Workforce,
  Year-on-Year, RAG Status, Sector Benchmark, Dynamic Titles and Labels)
- `power_bi/dax/_Measures.tmdl` — the exact `createOrReplace` export from Power BI Desktop's TMDL view;
  treat this as correct if it and the `.md` file ever disagree

### Standard measure patterns

```dax
-- £000s → £m conversion pattern (used by every base financial measure)
Total Income (£m) =
DIVIDE(SUMX(fact_ie_summary, fact_ie_summary[total_income_000s]), 1000, 0)

-- Percentage measure pattern
EBITDA Margin % =
DIVIDE(
    SUMX(fact_kpis, fact_kpis[ebitda_000s]),
    SUMX(fact_kpis, fact_kpis[total_income_000s]),
    BLANK()
) * 100

-- Year-on-year pattern: resolve the prior year, then re-evaluate a base measure against it
Prior Year Income (£m) =
VAR _py = [Prior Year]
RETURN IF(
    NOT ISBLANK(_py),
    CALCULATE([Total Income (£m)], dim_financial_year[financial_year] = _py),
    BLANK()
)

-- RAG status measure
EBITDA RAG =
VAR _margin = [EBITDA Margin %]
RETURN
    SWITCH(
        TRUE(),
        ISBLANK(_margin), "Grey",
        _margin >= 5,      "Green",
        _margin >= 2,      "Amber",
        "Red"
    )
```

## Visual Standards

- Use the verified NHS RAG palette for anything tied to a RAG status — these four values are read
  directly out of the `*RAG Colour` measures, not approximated:
  - Green (sustainable): `#009639`
  - Amber (at risk): `#FFB81C`
  - Red (unsustainable): `#DA291C`
  - Grey (no data): `#E8EDEE`
- General NHS brand colours for non-RAG chart series: NHS Blue `#003087`, NHS Dark Blue `#002060`, NHS
  Bright Blue `#0072CE`, NHS Orange `#ED8B00`
- All charts: remove gridlines, keep axis labels clean
- No 3D visuals

## Do Not

- Do not create measures inside report visuals — all measures go in `_Measures`
- Do not use implicit measures (auto-sum from column drag)
- Do not filter by calendar month — always use `dim_financial_year[financial_year]`; there is no monthly
  period grain anywhere in this project (TAC data is annual only)
- Do not use `SUMX` over `fact_income_detail` or `fact_expenditure_detail` for anything but the drilldown
  visuals they were built for — pre-aggregate in the SQL views (`fact_kpis`, `fact_ie_summary`, etc.)
  instead
- Do not add a `Var vs Budget` / YTD-style measure without checking first — this project has no budget or
  monthly-actuals data source; TAC is actuals-only, annual-only
